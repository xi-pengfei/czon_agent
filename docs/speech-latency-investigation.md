## 可确认的本地问题与修正

- 原方案在连续讲话时约攒满5秒才发第一段，再串行请求ASR。现首段上限2.5秒，后续仍约5秒；停顿优先分段，保留尾段。依然不是流式ASR。
- 原来直接使用浏览器默认AudioContext采样率。现优先请求16kHz，不支持时回退默认采样率，WAV头始终采用实际采样率。
- ASR和TTS原来共用两个并发名额；现分别两个名额，避免播报占满名额时拒绝录音识别。业务任务并发数不变。
- ASR原使用45秒网络超时，前端25秒取消。现ASR读超时15秒，连接、上传及连接池超时各3秒；前端仍有25秒总等待限制。网络各阶段超时不等同于严格的服务端全程截止时间；同步云端调用不能保证在浏览器断开瞬间取消。
- 等待6秒后说明识别服务响应慢并显示待处理分段数，已识别文字保留。
- 新增 `speech_request` 日志，记录ASR/TTS/摘要端点整体耗时、HTTP状态、服务器生成的请求ID；ASR新增上游耗时，TTS新增缓存/上游耗时。响应头带 `X-Speech-Request-ID` 与 `Server-Timing`。不记录录音内容、识别原文、口播文本或API密钥。

不能据此认定所有语音延迟已经解决。新日志生效后，应结合手机实际请求逐段定位。字幕逐字更新需要真正的实时ASR服务，本次没有更换平台或模型。
